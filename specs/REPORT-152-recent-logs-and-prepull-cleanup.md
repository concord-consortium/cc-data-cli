# cc-data-cli: recent logs, and removing the CLUE pre-pull settings

**Jira**: https://concord-consortium.atlassian.net/browse/REPORT-152

**Status**: **Closed**

## Overview

`cc-data get recent-logs <class-id>` pulls a class's log events from the last day or two, about two minutes behind live, into a dataset, and each later pull asks only for what is new. The CLUE pre-pull's leftovers (`clue_prepull` in new manifests, the local refusal for it, and `clue_source` in `scope.json`) go, in cc-data-cli and in the Researcher Dashboard runner, because packages now read CLUE only through cc-data.

A Researcher Dashboard package could so far see a class's logs only through a Student Actions run, which reads the nightly copy and lags by up to a day. REPORT-150 gave report-server a route that answers a class's recent events within minutes; this story is the cc-data side, so a package (and a researcher at a terminal) can show what students did minutes ago. REPORT-189's CLUE Dataflow package is the first consumer. The runner half (R20) is its own PR in researcher-dashboard, on branch `REPORT-152-drop-clue-source`.

## Requirements

### Pulling recent logs

- **R1. The command.** `cc-data get recent-logs <class-id> --dataset <ref> [--start <time>] [--end <time>] [--refresh]`. `<class-id>` is the portal's positive integer class id. It calls REPORT-150's route on the dataset's portal's report server with the stored API token, as every `get` does, and the dataset must already exist.
- **R2. What it asks for.** With no flags, it sends the cursor stored for this dataset and class (R4) when there is one, and otherwise nothing, which reads the whole window. `--refresh` ignores the stored cursor and reads the whole window: the backstop for an event delivered later than the cursor's ten-minute margin. `--start` and `--end` are sent instead of any cursor; each takes epoch milliseconds or an RFC 3339 time and is sent as epoch milliseconds. `--refresh` with either is a usage error, and so is an `--end` not after `--start`. Whether a bound falls inside the window is the server's check, whose 400 names `window_start`.
- **R3. An expired cursor.** When the server answers 410 `EXPIRED_CURSOR` to a stored cursor, the command drops that cursor, re-reads the whole window in the same invocation, and warns that events between the previous pull and `window_start` are not in `recent_logs` and come from a Student Actions run. The result says it happened (R10). Any other refusal of a stored cursor, a 400 included, is an error: REPORT-150 answers 410 to a cursor whose format it no longer reads.
- **R4. The stored cursor.** cc-data keeps one cursor per dataset and class: the `next_cursor` of the last pull that sent no `--start` and no `--end`, stored only after that pull's rows are in the store. A pull with `--start` or `--end` neither uses nor changes it, since its rows do not cover everything since the stored cursor. The cursor is the server's value, echoed as received; cc-data never decodes it and never derives one from the rows.
- **R5. Reading the response.** The body is streamed, with no size cap and no per-attempt deadline beyond the caller's context, since the server alone may wait 60 s before the first byte. Failures before the first byte (transport errors, 429, 5xx) are retried as streamed downloads are, but with two attempts in all rather than six, because each attempt that reaches Athena starts a query the server does not stop. A body that ends early or does not parse, a `class_id` that is not the one asked for, or a `count` that differs from the rows read stores nothing and leaves the cursor as it was, and the command exits with an error.
- **R6. What is stored.** Each row exactly as received: the 13 columns, `parameters` and `extras` kept as the strings they are (never JSON-decoded at fetch), plus `_fetched_at` (the pull's time) and `_class_id` (the class asked for). A row whose `id` is absent, null, not a string or empty fails the pull with `MALFORMED_ITEM` naming the class, storing nothing and leaving the cursor, as REPORT-110's R5 does for a CLUE item without its identity.
- **R7. The `recent_logs` store.** One store per dataset, keyed by `id` alone, holding every class pulled into the dataset. A row pulled again replaces the stored one (the newer pull wins), so overlapping pulls never duplicate an event. **A pull never removes a row**: rows that have left the route's window, and rows another class's pull added, stay until `dataset purge` or `dataset delete`.
- **R8. Pinned column types.** `id`, `session`, `application`, `activity`, `event`, `event_value`, `parameters`, `extras` and `run_remote_endpoint` are VARCHAR; `time`, `timestamp`, `user_id`, `primary_user_id` and `_class_id` BIGINT; `_fetched_at` TIMESTAMP. The types hold whatever values a pull happened to see, including a column that is null in every row so far, and match `logs`' CSV types for these columns.
- **R9. The download record.** The dataset's manifest holds one download entry per class pulled, of type `recent_logs`, carrying the class id, the last pull's `window_start`, `since`, `until`, `query_started_at`, whether it completed, its merge counts, and the stored cursor (R4). `dataset show` lists it by class, and its `--json` entry has `class_id` and no `run_id`. `dataset purge` clears it with the store. `dataset reindex` recovers the store and the entry from disk; a reindex with no prior manifest to carry the cursor from loses it, and the next pull reads the whole window.
- **R10. The result.** Progress goes to stderr; the result line (and the MCP tool's result) is a JSON object with `type` (`recent_logs`), `class_id`, `window_start`, `nightly_through`, `since`, `until`, `query_started_at`, `latest_timestamp`, `rows` (rows received), `merge_counts` (`fetched`, `new`, `updated`, `removed`, the last always 0), `cursor` (`stored`, `unchanged` or `none`, the last for a pull with `--end`), and `expired_cursor` (R3).
- **R11. Concurrency and interruption.** Two pulls of the same class into one dataset do not run at once: the second fails "download busy", as other fetches do. Pulls of different classes may run at once and merge one after another. An interrupted pull leaves the store and cursor as they were, or its rows merged with the cursor not yet advanced; never a cursor ahead of the rows it promises.
- **R12. The MCP tool.** `get_recent_logs` takes `dataset`, `class_id`, and optional `start` and `end` (strings in either form R2 accepts) and `refresh`, with R2 to R11's behavior and R10's result. Its description also carries the three facts a wrong count most often comes from, since an MCP-only client is not shown `core.md`'s view catalog: the rows are in the `recent_logs` view, not `logs`; an event a log run also holds appears in both views; and order by `received_time`.

### The view

- **R13. `recent_logs`.** A static view registered on every dataset: every stored row with all its columns, plus `logs`' four derived columns computed the same way (`parameters_json`, `extras_json`, `event_time` from `time` in seconds, `received_time` from `timestamp` in milliseconds). With no store it is empty with the same columns. It is materializable as the store views are.
- **R14. Apart from `logs`.** `logs` is unchanged and does not include recent rows. No per-class view is added, and `run_membership` gains no rows for `recent_logs`, which has no runs.
- **R15. `downloads` names the class.** The `downloads` view gains a `class_id` column, NULL for run downloads; a `recent_logs` row has a NULL `run_id`.

### Removing the pre-pull's settings

- **R17. `clue_prepull`.** `package init` writes no `clue_prepull`. cc-data no longer reads the key: a manifest that still has it, `true` or `false`, is run, built and published like any other, with the key left in the file as the author wrote it.
- **R18. No refusal.** `cc-data package run` no longer refuses any package for CLUE. `Refused`'s comment, `runDifferences` in `cmd/package.go` and the researcher guide's "CLUE" bullet under what `run` cannot reproduce lose their mention of it.
- **R19. `clue_source`.** `scope.json` as `package run` writes it holds `kind`, `id`, `classes`, `assignments`, `dataset` and `output_dir`, in that order, and no `clue_source`. Nothing in cc-data-cli reads or writes `clue_source`.
- **R20. The runner.** researcher-dashboard's runner writes `scope.json` without `clue_source`: `CLUE_SOURCE` and its comment go from `runner/server/package-env.js`, and `runner/test/package-env.test.js` asserts the six keys in order. It can merge before or after cc-data-cli's PR, since nothing reads the key. *(Its own PR in researcher-dashboard, branch `REPORT-152-drop-clue-source`, not part of this branch.)*

## Technical Notes

- **REPORT-150's route** (report-service, branch `REPORT-150-report-server-the-class-scoped`, closed spec `specs/REPORT-150-class-scoped-recent-logs-route.md`). `GET /api/v1/classes/:class_id/recent-logs` reads REPORT-107's `logs_by_hour` for the class's learners, joined by `run_remote_endpoint`, from `window_start` (00:00 UTC yesterday) onward.
  - Optional `start`/`end` (epoch ms, inside the window) narrow the read; a `cursor` cannot be combined with either (400).
  - A request with no `end` answers `next_cursor`, opaque, whose version 1 holds the class id and `since = query_started_at - 10 minutes`, so responses overlap and the caller dedups by `id`. A cursor older than `window_start`, or in a well-formed version the server no longer reads, is 410 `EXPIRED_CURSOR`; a malformed one or another class's is 400.
  - The body is one JSON object streamed as Athena is read: `class_id, window_start, nightly_through` (an ISO date), `since, until, query_started_at`, then `rows`, then `count, latest_timestamp, next_cursor`. A failure after the first byte closes the connection mid-body. `next_cursor` is null exactly when `until` is set; a class with no learners answers `rows: []` with `count: 0` and a cursor.
  - Rows carry the 13 `student-actions` columns; `time`, `timestamp`, `user_id`, `primary_user_id` are integers, the rest strings, an empty field `null`. 503 when the Athena query does not finish within 60 s or more than four reads are in flight; 422 above about 2,100 learners.
- **CLUE log rows.** CLUE logs only when launched from the portal (`collaborative-learning` `src/lib/logger.ts`), and its `run_remote_endpoint` is the learner's `remote_endpoint_url`, the key the route joins on. A staging CLUE class answers rows only for students launched from the staging portal; demo and QA modes log nothing.
- **The registry fields** (`internal/store/kind.go`). `recentLogsKind`: identity `id`, `Strict`, R8's pins, no route, `ClassKeyed` and `Accumulate`.
  - `ClassKeyed`: the integer in the kind's segment and membership names is a class id. `Kind.StampColumn()` gives `_class_id`, and `Kind.StampLines` stamps a page in it, which the fetch then writes with `AppendLines`; `StampLines`, which `FetchPaged` calls, keeps `_run_id`. `MultiSource`'s tie-break (`readStamp`) reads `_run_id`, falling back to `_class_id`. `run_membership`, its identity columns (`store.IdentityColumns()`), the per-run views and `query --help`'s per-run list (`perRunStoreNames`) leave the kind out. `Download.Key()` reads `ClassID`.
  - `Accumulate`: `StreamMerge` keeps every old record, so `openCovered` walks no membership and a merge never removes a row, whatever state the membership files are in. `Dataset.WriteMembership(m, typ, run, version, idx)` writes the union of the merging class's old membership and the segment's keys through `(*SegmentIndex).WriteMembershipWith`, a merge walk of two key-ordered streams; a membership file the manifest names but the disk lacks fails that merge closed. The membership files serve reindex, which rebuilds each class's entry from them; it adopts the kind's newest store version on disk without the membership-at-the-same-version check other kinds need, since that version holds every older one's rows.
- **The download entry** (`internal/dataset/manifest.go`). `Download` has `ClassID` and `RecentLogs *RecentLogsPull` (window, `since`, `until`, `query_started_at`, `nightly_through`, `latest_timestamp`, `rows`, `cursor`). `DownloadJSON`'s `run_id` is `omitempty`, so a `recent_logs` entry has `class_id` and no `run_id`; run ids start at 1, so no other entry changes. `sameDownload` compares `ClassID`. Reindex rebuilds a class's entry from its membership key and carries `RecentLogs` from the prior manifest; it also carries forward a prior class entry with no membership on disk (a pull that returned no rows merges nothing but records the cursor), and drops one with no class.
- **The fetch** (`internal/fetch/recentlogs.go`). The body streams to a file through `StreamAPIToFile` on a client copy with `RecentLogsMaxAttempts` (2). `Client.getJSON`'s 60 s deadline and 64 MiB cap would not fit the route. `api.IsPartialDownload` lets the fetch replace the report-CSV wording of a cut-off body with its own, keeping `TRANSIENT`. `decodeRecentLogs` walks the top-level object with `json.Decoder`, hands rows to the segment in 500-row batches byte for byte, reads each `id` with `store.IdentityFromRecord`, and requires EOF after the closing brace. A cut before the closing fields fails only after the earlier rows were yielded, so nothing is merged and no cursor written until the decode returns cleanly. Errors: a cut or unparseable body is `TRANSIENT`; a row without its `id` is `MALFORMED_ITEM`; a `class_id` or `count` mismatch, or a row that is not a JSON object, is `BAD_RESPONSE`. A finished, unmerged segment left from a crash is merged before the next request.
- **The view** (`internal/duck/views.go`). `recentLogsView` is built with REPORT-111's `clueSource` and `clueView`, adding `logDerived`'s four columns; a missing store file warns as the CLUE stores do. `downloads` renders `class_id` and a recent-logs `run_id` as `CAST(NULL AS BIGINT)`, since a bare `NULL` in `VALUES` types the column `"NULL"` when no row has a value.
- **Size.** Each merge rewrites the whole store, as answers and history do. One class's share of a production day (about 170 MB of logs across every application) is small, so a semester of one class's pulls is tens to a few hundred MB rewritten per pull. Not optimized here.
- **Mixed versions.** Downgrading is unsupported. A cc-data older than this release cannot open a query session on a dataset holding a `recent_logs` membership (its per-run loop builds `recent_logs_<class>` over a view it lacks). One that only rewrites the manifest drops `class_id` and `recent_logs` from the entry; the next pull reads the whole window, and reindex drops the classless entry.
- **The pre-pull's settings.** report-server reads a missing `clue_prepull` as `false` and ignores unknown keys, and no package reads `clue_source`, so the cc-data-cli and runner removals merge in either order.

## Decisions

### Requirements

- **The cursor lives on a `recent_logs` download entry keyed by class.** Purge and show already handle entries, and `downloads` can say which classes a dataset pulled. A separate manifest map or a sidecar file would each need their own purge, show and reindex handling. The cost is `downloads.class_id`.
- **Only a pull with no `start` and no `end` moves the cursor.** The cursor promises everything before its `since` is stored; a `start`-only pull's cursor would skip the gap before `start` forever.
- **A 410 re-reads the window once, with a warning.** Failing would break a package's first pull after every weekend; the re-read is what `--refresh` does, and the warning names the gap.
- **A row without its `id` fails the pull** (Doug, 2026-10-22). The ingester gives every event an `id` and REPORT-107 reconciled 1.8M production rows by it, so this is about one contract rule shared with REPORT-110. Hashing other columns would invent an identity REPORT-192 could never match.
- **The acceptance package is not committed.** Its laptop half needs live staging data no CI run has, so a committed package would be a fixture no test runs. REPORT-189 is blocked by this story, so it cannot be the acceptance.
- **The runner's half is specced here.** It is a few lines whose reason is R19, and RD-4 pass 2's spec defers the key to this story by name.
- **Two attempts on the route, not six** (Doug, 2026-10-22). Each attempt reaching Athena starts a query the server does not stop; two bounds a slow class at one orphaned query and still retries a full limiter once.
- **`id` stays out of the guarded identity-columns list.** That list is the `run_membership` join key, which `recent_logs` has none of; a prose line names its key instead, and REPORT-110's guard is unchanged.
- **A 400 on a stored cursor stays an error** (Doug, 2026-10-23). The server owns the cursor's format, so REPORT-150 answers 410 to a version it retired; inferring expiry from a generic 400 would hide a client bug as a silent full re-read.
- **The pre-release tag and the runner pin are this story's acceptance** (Doug, 2026-10-23), with the pin in its own researcher-dashboard PR so R20 still merges in either order.

### Implementation

- **The class id rides in the run's integer slot in segment and membership names, and in its own `ClassID` on the download.** Merge, sweep and reindex stay unchanged apart from the union; a class id in `Download.RunID` would read as a run in every join.
- **Stream the body to a file, then decode it.** It reuses the streamed-download path's retry and truncation rules, and the decode is local and restartable.
- **The download entry is written only once the pull has merged.** An incomplete entry would need the old cursor carried through and an INCOMPLETE warning for intact rows; writing once removes the state.
- **An accumulating merge removes nothing by construction, rather than by every class's membership covering its rows** (code review). Under the covered walk, a class whose membership file was lost and then reindexed away had its rows deleted by another class's next pull, while its stored cursor skipped them; and a lost membership file at the newest version left reindex adopting no store at all, so the next pull rewrote it from one class's rows.
- **Two `Kind` fields, `ClassKeyed` and `Accumulate`.** The stamp column, the views and the download key all follow from the key being a class, so one field keeps them from disagreeing.
- **The stamp column comes from the kind.** `Kind.StampLines` stamps in `StampColumn()`, so no run-keyed caller changes and no existing kind's stamp changes.
- **The store and the view land as one commit.** Registering the kind registers its view through REPORT-110's loop, which turns the docs and identity-column guards red until the view and its guarded docs exist.
- **A pull that returns no rows writes no segment but still records its entry and cursor.** Merging nothing is correct, and the cursor still moves past the empty window.
- **`MALFORMED_ITEM` for a missing `id`, `BAD_RESPONSE` for envelope mismatches and non-object rows.** The first matches REPORT-110's code for a CLUE item without its identity.
- **The MCP handler checks the fetch's error itself rather than going through the shared result helper.** A nil typed map passes that helper's type assertion, so the error would come back as an empty success.
